# Indie Atlas 実装仕様

版: v0.2（2026-10-27）。草案 v0.1（同日作成）を、実装担当者がそのまま作業に着手できる粒度に具体化したもの。

Indie Atlas は、インディーゲームのライブラリ兼ショーケースである。GitHub Actions で LLM を定期実行し、作品の発見、作品情報の補完、外部記事との関連づけ、コレクションの更新を続ける。初期は GitHub Pages で公開する。発見体験と自動更新の価値を確認できたら、独自ドメインと別ホストへ移行する。

## 記号と用語

### 確定度の表記

| 表記 | 意味 | 実装時の扱い |
| - | - | - |
| 【確定】 | 合意済みの方針 | 変更する場合は利用者の合意が必要 |
| 【初期案】 | 本仕様が定める既定の設計 | そのまま実装する。より良い案があれば、文書を更新してから実装する |
| 【要決定】 | 利用者の判断が必要な項目 | [11-open-decisions.md](11-open-decisions.md) の既定値で実装し、差し替えやすくしておく |

### 用語集

| 用語 | 英語名（コード上） | 意味 |
| - | - | - |
| 作品 | Game | 収録対象のゲーム。本編を単位とし、体験版や DLC は本編に付属させる |
| 開発者 | Developer | 開発者またはパブリッシャー。個人とスタジオの両方を含む |
| 記事 | Article | 外部媒体の記事。記事を識別する情報と作品との関連だけを保存し、本文は保存しない |
| 個別情報 | Claim | 作品について出典が示す1つの主張。発売日、機種、日本語対応など |
| 根拠 | Evidence | Claim を支える出典。URL、取得日時、短い抜粋を持つ |
| 採用 | adopted | 決定的なコードが検証し、サイトに表示すると決めた状態 |
| 候補 | candidate | 保存はしたが、まだ表示しない状態 |
| 情報源 | Source | 定期的に取得する媒体、ストア、イベントページなど |
| タスク | Task | 調査の単位。目的、対象、優先度、状態、再確認の条件を持つ |
| 実行 | Run | GitHub Actions の1回のワークフロー実行 |
| 調査ジョブ | research job | LLM が外部情報を読み、更新の提案を作るジョブ。書き込み権限を持たない |
| 提案 | Proposal / Operation | 調査ジョブが出力する構造化された変更案 |
| 採用ジョブ | adopt job | 提案を検証してデータに反映し、コミットするジョブ。LLM を呼ばない |
| 公開内容ハッシュ | contentHash | 公開に影響する入力から計算するハッシュ。公開を省略するかどうかの判定に使う |
| 探索枠 | exploration quota | 未収録作品や報道の少ない作品の調査に、毎回確保する予算 |

## 実装担当者への指示

1. 段階の順に実装する。チケットと完了条件は [09-roadmap.md](09-roadmap.md) にある。後の段階のための拡張点は残してよいが、先回りして実装しない。
2. 仕様の要件どうしが衝突したら、次の順で優先する。
   1. 安全性。権限の分離、機密情報の保護、外部入力の隔離
   2. データの正しさ。根拠のない情報を公開しないこと、作品を誤って統合しないこと
   3. 再実行しても整合性が保たれること
   4. 利用者の体験
   5. 実装の簡潔さ
3. 仕様と異なる実装が必要になったら、先に該当する文書を更新し、[11-open-decisions.md](11-open-decisions.md) の決定ログに日付と理由を追記する。
4. テストから LLM と外部サイトを実際に呼ばない。Fake のアダプタとフィクスチャを使う（[10-testing-and-acceptance.md](10-testing-and-acceptance.md)）。
5. 人が出典を確認していないデータを、初期データやテスト期待値として実在の作品名で作らない。テスト用には架空の作品を使う。
6. 機密情報（API キーなど）は GitHub Actions の Secrets からだけ読み込む。リポジトリ、ログ、成果物、公開サイトに含めない。
7. コミットは変更のまとまりごとに分ける。コミットメッセージは英語の Conventional Commits 形式にする（例: `feat(site): add game detail page`）。
